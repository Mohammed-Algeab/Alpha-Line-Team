# خارطة تطوير Alpha Line بعد النسخة الأولى

## الهدف

يهدف هذا المسار إلى نقل **Alpha Line / ألفا لاين** من نموذج بصري ومحتوى تجريبي مكتمل البنية إلى موقع عام موثوق وسهل الإدارة، من دون فقدان ميزة الموقع الثابت: صفحات HTML مستقلة وسريعة وقابلة للفهرسة، ومحتوى محفوظ داخل المستودع ويمكن مراجعته قبل النشر.

> **القرار المعماري المبدئي:** لا توجد حاجة حالية إلى قاعدة بيانات أو لوحة إدارة أو خادم دائم. يستمر الموقع على Astro مع محتوى محلي، لأن فريق العمل صغير والمحتوى التحريري يحتاج مراجعة مقصودة قبل ظهوره.

## صورة الوضع الحالي

| المجال | الحالة الحالية | ما ينبغي تطويره |
|---|---|---|
| البنية العامة | Astro يولّد صفحات ثابتة مستقلة للتعريبات والتصنيفات والمدونة والإصدارات. | تنظيف بقايا مشروع React القديم وتقليل الحزم غير المستخدمة. |
| إدارة المحتوى | ملفات JSON لكل مشروع ومدونة، مع اختيار مشروع مميز واحد عبر `feature`. | توسيع النموذج للتحقق من صحة الحقول، وفصل النصوص الطويلة والإصدارات عند نمو المحتوى. |
| التصميم | اتجاه «أطلس المسارات» مكتمل بصريًا، وواجهة الهاتف الداكنة متماسكة. | تحسين التفاصيل الوظيفية فقط: حالات فارغة، إمكانية الوصول، وحركات دقيقة غير مشتتة. |
| البحث | بحث محلي بسيط داخل الصفحة باستخدام مطابقة نصية مباشرة. | فهرس ثابت أفضل، ترتيب نتائج، وفلاتر عملية عند زيادة عدد المشاريع. |
| SEO والمشاركة | العنوان والوصف والرابط القانوني وخريطة الموقع موجودة. | ضبط الدومين الحقيقي، صور المشاركة لكل مشروع، وبيانات منظمة محسّنة. |
| الإطلاق | معاينة محلية تعمل، بينما الاستضافة العامة لم تُربط بعد. | مستودع GitHub، Cloudflare Pages، الدومين، وفحص قبل النشر. |

## ما لا يحتاجه الموقع الآن

لا يوصى ببناء لوحة إدارة، أو تسجيل دخول، أو قاعدة بيانات، أو نظام تعليقات، أو إشعارات فورية قبل وجود فريق متعدد الأعضاء ومحتوى يتغير بكثافة. هذه المزايا ستزيد الإدارة والأمان والتكلفة، ولا تحل مشكلة الإطلاق الحالية التي تتمثل في إنتاج تعريب حقيقي ومحتوى دقيق عنه.

كذلك لا يوصى بإضافة صفحات كثيرة لمجرد اكتمال خريطة الموقع. يجب أن يضاف كل قسم عندما يمتلك وظيفة أو محتوى حقيقيين؛ فصفحة الخطط، أو المعرض، أو فريق العمل لا ينبغي نشرها بصيغة فارغة.

## المرحلة 1: جعل المحتوى حقيقيًا وقابلًا للنشر

تبدأ المرحلة باختيار أول لعبة فعلية والتعامل معها كـ«مشروع مرجعي» يحدد مستوى بقية الموقع. تُستبدل مشاريع العرض بمعلومات مؤكدة عن اللعبة، وتُكتب النبذة وقصة التعريب بلغة واضحة غير تسويقية، وتُضاف المنصات المدعومة وحالة العمل وروابط القنوات المناسبة. لا ينبغي إعلان تاريخ إصدار ما لم يكن الفريق واثقًا منه.

| العمل | التفاصيل | معيار الاكتمال |
|---|---|---|
| المشروع الأول الحقيقي | اسم اللعبة الأصلي والعربي، السلسلة، وصف بلا حرق، الغلاف، المنصات، حالة المشروع، ونص قصير عن سبب اختياره. | صفحة المشروع مفيدة حتى قبل وجود إصدار قابل للتنزيل. |
| سياسة الحالة | اعتماد قاموس ثابت مثل: قيد الدراسة، في التحضير، قيد العمل، قيد المراجعة، متاح، مؤرشف، متوقف. | لا تظهر حالات مبهمة أو وعود زمنية متناقضة. |
| بيانات الإصدار | رقم إصدار التعريب، إصدار اللعبة المتوافق، التاريخ، الملاحظات، الرابط، الحجم، وربما قيمة تحقق للملف. | يستطيع اللاعب معرفة ما يناسب نسخته وكيفية التثبيت. |
| القنوات | استبدال روابط تيليغرام وديسكورد والبريد التجريبية بالقنوات الرسمية. | لا توجد أزرار تقود إلى رابط تجريبي في الموقع العام. |

## المرحلة 2: رفع جودة نموذج المحتوى

يحافظ الموقع على JSON في المرحلة التالية، لكن يتطور إلى نموذج أكثر أمانًا: تفصل بيانات اللعبة الثابتة عن بيانات مشروع التعريب المتغيرة وسجل الإصدارات. تنتقل المقالات والتعليمات الطويلة تدريجيًا إلى Markdown، بينما تبقى البيانات الصغيرة المنظمة في JSON. هذا يجعل تعديل التثبيت أو نشر إصدار جديد أقل عرضة للأخطاء.

تنفذ عملية تحقق وقت البناء باستخدام مخطط بيانات: يتأكد من وجود `slug` فريد، وترتيب صحيح، وحالة معتمدة، ورابط تحميل صحيح لكل إصدار منشور، وعدم تعارض المشروع المميز. يمكن كذلك استبدال `feature: true` مستقبلًا بحقل صريح مثل `featuredOrder` فقط عندما تقرر الصفحة الرئيسية عرض أكثر من مشروع مميز.

| مستوى المحتوى | البنية المقترحة عند الحاجة | الفائدة |
|---|---|---|
| لعبة | بيانات ثابتة: الاسم، الناشر، السنة، المنصات، الروابط الرسمية، الغلاف. | لا تتكرر تفاصيل اللعبة بين أكثر من تعريب أو إصدار. |
| مشروع تعريب | الحالة، الوصف، قصة التعريب، الفريق، الوسائط، بيانات SEO. | صفحة الدوسيه تبقى واضحة وقابلة للتوسع. |
| إصدار | التوافق، التنزيلات، الحجم، التجزئة، ملاحظات التغيير، الاستقرار. | تمييز صريح بين تحديث اللعبة وإصدار التعريب. |
| نص طويل | Markdown لتعليمات التثبيت والأسئلة الشائعة ومقالات التحديث. | قراءة وتحرير أسهل من حقل JSON طويل. |

## المرحلة 3: تحسين التجربة الوظيفية من دون تغيير الهوية

يبقى اتجاه «أطلس المسارات» كما هو، وتقتصر التحسينات على جعل التفاصيل أكثر خدمة للمستخدم. الأولوية هي أن يصل اللاعب بسرعة إلى حالة التعريب، الإصدار المتوافق، طريقة التثبيت، ومكان طلب المساعدة.

تضاف حالات فارغة واضحة عندما لا توجد مشاريع في تصنيف، ورسائل منطقية عند عدم إيجاد نتيجة في البحث، وروابط رجوع من الصفحات الفرعية. ويُحسن البحث لاحقًا عبر فهرس JSON مولّد وقت البناء، يدعم العنوان العربي والإنجليزي والسلسلة والحالة والكلمات المفتاحية، مع ترتيب النتائج وفلاتر للمنصة والحالة والسلسلة.

| التحسين | الأثر على المستخدم | متى ينفذ |
|---|---|---|
| بحث ثابت محسّن | يجد المشروع بالاسم العربي أو الإنجليزي حتى مع تعدد المحتوى. | عند تجاوز نحو 8–10 مشاريع أو مقالات. |
| فلاتر الأرشيف | فرز سريع حسب السلسلة والحالة والمنصة. | عند تنوع المشاريع فعليًا. |
| FAQ وسياسة استخدام | تقليل أسئلة التثبيت المتكررة وشرح طبيعة التعريبات غير الرسمية. | قبل أول إصدار عام. |
| صفحة 404 موجهة | إعادة الزائر إلى الأرشيف أو البحث بدل نهاية مسدودة. | قبل الإطلاق العام. |
| صفحة بلاغ مشكلة | توجيه المستخدم إلى قناة ديسكورد أو قالب بلاغ منظم. | بعد تفعيل قناة الدعم. |

## المرحلة 4: SEO والمشاركة والأداء وإتاحة الاستخدام

قبل الإطلاق، يُضبط `SITE_URL` إلى الدومين الحقيقي حتى تُنتج الروابط القانونية وخريطة الموقع عناوين نهائية. يضاف عنوان ووصف وصورة مشاركة لكل صفحة مشروع، مع صورة افتراضية متناسقة للفريق. تُضاف بيانات منظمة دقيقة فقط عندما تتوفر البيانات الحقيقية، مثل Organization للموقع وVideoGame للعبة وSoftwareApplication أو CreativeWork للإصدار عند انطباقها.

تشمل المراجعة كذلك ضغط صور الأغلفة، واستعمال صور بأبعاد ثابتة، وإتاحة نص بديل وصفي، وتدقيق تباين الألوان، والتنقل بلوحة المفاتيح، واحترام تفضيل تقليل الحركة. لا ينبغي إضافة مؤثرات حركة جديدة إلا إذا أوضحت انتقالًا أو حالة؛ فالمسار السماوي يجب أن يوجه النظر لا أن يتحول إلى طبقة HUD مزدحمة.

## المرحلة 5: التنظيف التقني والجودة المستمرة

تُزال حزم React وWouter وواجهة العميل السابقة والإعدادات الموروثة التي لم تعد تدخل في بناء Astro. هذا يجعل مصدر المشروع واضحًا: Astro وTypeScript وCSS وبيانات المحتوى فقط، ويقلل حجم التثبيت والصيانة وارتباك أي عضو ينضم للفريق.

تضاف فحوصات محلية قبل النشر: فحص Astro وTypeScript، بناء إنتاجي، تدقيق روابط داخلية، والتحقق من وجود صور وروابط تنزيل للحالات المنشورة فقط. لا يتطلب ذلك خادمًا دائمًا أو قاعدة بيانات؛ إنه جزء من عملية البناء ذاتها.

| الإجراء | الهدف | معيار النجاح |
|---|---|---|
| حذف التبعيات القديمة | تقليل سطح الصيانة ومنع خلط React وAstro. | `pnpm install` و`pnpm build` يعملان بحزمة Astro مركزة. |
| فحص المحتوى | كشف معرفات مكررة وروابط ناقصة وحالات غير معتمدة قبل النشر. | يفشل البناء برسالة مفهومة عند إدخال بيانات غير صالحة. |
| اختبار مسارات | حماية الروابط من التلف بعد إضافة صفحات أو تغيير slugs. | لا توجد روابط داخلية معطلة في إنتاج الموقع. |
| قائمة إطلاق | تكرار عملية تحقق بسيطة قبل كل إصدار أو تحديث كبير. | نفس الخطوات ينتج عنها موقع صالح دائمًا. |

## المرحلة 6: الدومين والنشر العام

ينشأ مستودع GitHub مفتوح المصدر بعد إزالة أي مفاتيح أو بيانات خاصة. تربط Cloudflare Pages بالمستودع مع أمر البناء `pnpm build` ومجلد الإخراج `dist`. بعد شراء الدومين، يُربط بالدومين الأساسي ويُضبط متغير `SITE_URL` ليطابقه. يضاف تحويل من النطاق البديل إلى النطاق الرسمي، وتتحقق شهادات HTTPS ثم تُرسل خريطة الموقع إلى أدوات مشرفي محركات البحث.

| خيار النشر | كيف يعمل | المزايا | التنازلات | تكلفة وتشغيل |
|---|---|---|---|---|
| نشر يدوي من الجهاز | يعدل المدير المحتوى ثم يبني ويرفع المجلد الناتج بنفسه. | أبسط بداية وأقصى تحكم. | احتمال نسيان خطوة بناء أو رفع ملف قديم. | منخفضة جدًا؛ عملية يدوية عند كل تحديث. |
| نشر عند دفع تعديل إلى GitHub | كل تعديل مُراجع في المستودع يولد الموقع ويحدث النشر تلقائيًا. | نسخة قابلة للتتبع، مراجعة سهلة، ولا يحتاج رفع يدوي. | يتطلب إعدادًا أوليًا للمستودع والاستضافة. | منخفضة جدًا؛ الأنسب عند تكرار التحديثات. |

لا يُبنى نظام نشر معقد أو لوحة إدارة في هذه المرحلة. يمكن لاحقًا، بعد اتساع الفريق، إضافة واجهة إدخال محمية تحفظ تعديلات المحتوى كمراجعة قابلة للموافقة في المستودع، ثم تعيد توليد نفس الموقع الثابت.

## المرحلة 7: إمكانات مؤجلة حتى يثبت الاحتياج

تؤجل هذه المزايا لأنها مفيدة فقط في حالة نمو حقيقي للفريق أو الجمهور: تعدد أعضاء التحرير مع مراجعات وصلاحيات، نموذج بلاغات منظم، تعليقات، تحليلات خصوصية، موجز RSS، صفحة حالة، PWA للتثبيت على الهاتف، أو لوحة إدارة. عند الحاجة إلى الإحصاءات، يفضل حل تحليلي خفيف ومحترم للخصوصية؛ وعند الحاجة إلى بلاغات كثيرة، يفضل نموذج أو قناة دعم منفصلة بدل جعل الموقع نفسه نظام تذاكر كاملًا.

## اختبار القبول قبل الإطلاق

| المحور | فحوصات القبول |
|---|---|
| المحتوى | كل مشروع منشور يحمل وصفًا وحالة ومنصة وتاريخ تحديث وصورة ورابط دعم مناسبًا. |
| الإصدارات | كل رابط تنزيل يوضح نسخة اللعبة المتوافقة وطريقة التثبيت والتنبيه القانوني إن لزم. |
| SEO | الدومين الحقيقي ظاهر في canonical وsitemap وOpen Graph، ولا تبقى روابط المثال. |
| الهاتف | الرأس، الأرشيف، صفحة المشروع، البحث، والتواصل قابلة للقراءة والضغط من شاشة هاتف ضيقة. |
| الروابط | جميع روابط التنقل والتصنيفات والإصدارات والقنوات الخارجية تعمل ولا توجد وجهات تجريبية. |
| البناء | ينجح `pnpm check` ثم `pnpm build` قبل كل نشر. |

## ترتيب التنفيذ المقترح

ابدأ بالمشروع الحقيقي الأول، وليس بإضافة تقنية جديدة. بعد اكتمال صفحة ذلك المشروع والقنوات الرسمية، اشترِ الدومين واربط النشر العام. قبل أول إصدار تحميل، أضف FAQ وسياسة استخدام وصفحة 404 وفحص محتوى بسيط. بعد أن يتجاوز الأرشيف عدة مشاريع، حسّن البحث والفلاتر. ولا تنتقل إلى لوحة إدارة أو قاعدة بيانات إلا عندما يصبح التعديل اليدوي عائقًا فعليًا لفريق متعدد الأعضاء.

## الافتراضات والمخاطر المفتوحة

تفترض هذه الخطة أن الموقع يبقى مفتوح المصدر وأن مسؤولًا واحدًا يراجع المحتوى حاليًا، وأن ملفات التنزيل تستضاف خارج المستودع. يجب تثبيت اسم الدومين قبل تنفيذ مرحلة SEO النهائية. كما يجب مراجعة حقوق استخدام أغلفة الألعاب وصورها وروابط التنزيل وسياسة كل منصة قبل النشر؛ لا ينبغي أن تُخزن ملفات اللعبة أو أصولها المحمية داخل مستودع الموقع.
