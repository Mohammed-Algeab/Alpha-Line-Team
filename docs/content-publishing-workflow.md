# سير عمل محتوى ونشر Alpha Line

> **الحالة:** خطة تشغيل أولية، تطبق بعد ربط المستودع وCloudflare Pages. لا تحتاج قاعدة بيانات أو لوحة إدارة.

## المبدأ

يبقى الموقع ثابتًا: ملفات JSON وMarkdown تصف المحتوى، وAstro يحولها إلى صفحات HTML عند البناء. النشر الآلي ليس «موقعًا ديناميكيًا»؛ إنه بناء جديد للملفات الثابتة بعد تغيير موثق في GitHub.

## سير العمل الأساسي

| المرحلة | المسؤول الأولي | الإجراء | النتيجة المطلوبة |
|---|---|---|---|
| 1. إعداد المحتوى | المالك | تعديل ملف مشروع أو مقال عبر قالب معتمد | بيانات كاملة بلا روابط أو معلومات خاصة. |
| 2. معاينة محلية | المالك | تشغيل `pnpm dev` وفحص الصفحة والتخطيط | التأكد من النصوص والروابط والبطاقات قبل الرفع. |
| 3. تحقق البناء | النظام محليًا أو GitHub | تشغيل `pnpm build` | كشف أخطاء JSON والروابط والقيم الناقصة قبل الإنتاج. |
| 4. مراجعة التغيير | المالك | مراجعة الفرق في Git قبل الدمج | لا رابط تنزيل خاطئ، ولا معلومات خاصة، ولا محتوى غير جاهز. |
| 5. نشر تلقائي | Cloudflare Pages | بناء فرع الإنتاج ونشر الناتج الثابت | صفحات HTML محدثة قابلة للفهرسة وفق قواعد الموقع. |
| 6. تحقق بعد النشر | المالك | فتح صفحة المشروع وروابط التنزيل مباشرة | إصلاح سريع إن ظهرت مشكلة فعلية. |

## التعاون المستقبلي

لا يمنح أعضاء الفريق صلاحية نشر مباشرة في البداية. عند الحاجة، يستطيع المحرر الموثوق إما اقتراح تغيير عبر فرع أو طلب سحب، أو ملء قالب JSON/Markdown يراجعه المالك. ويظل دمج التعديل في فرع الإنتاج مسؤولية شخص واحد حتى تستقر قواعد العمل.

## الحماية والنسخ

يبقى تاريخ GitHub النسخة الأولى من ملفات الكود والمحتوى النصي. لا تدخل الروابط الخاصة أو رسائل البريد الشخصية أو الأصول غير المرخصة إلى المستودع العام. أما الصور المنشورة في Cloudflare R2 وروابط التنزيل الخارجية، فتوثق في ملفات المحتوى العامة فقط عندما تصبح جاهزة للزوار.

## قرار مؤجل

يمكن تحديد نافذة نشر يومية أو أسبوعية لاحقًا إذا زاد عدد المساهمين. لا تفرض هذه القاعدة في المرحلة الأولى، لأن الإصلاحات العاجلة وروابط التنزيل الخاطئة يجب أن تبقى قابلة للتصحيح فورًا.
